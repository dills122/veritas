# GitHub repository setup

The repository is [dills122/veritas](https://github.com/dills122/veritas), with `main` as the default branch. The initial reviewed implementation was pushed as `5d696d3c876e4e81021834cff2c7ab69a5be91af`. The original candidate closure and review reports remain historical evidence for that implementation. This setup adds repository automation without reopening the completed product tasks.

## Checks and maintenance

- **Quality and unit tests:** lint, formatting, strict TypeScript, unit tests and planning consistency on Ubuntu.
- **Candidate (macos-latest / ubuntu-latest):** integration tests, clean installed package, public declarations, 42 CLI example commands and eight core example checks. Each runner uploads a tarball, SHA-256 checksum and example receipts for 30 days.
- **Dependency audit:** high/critical vulnerability gate on pushes, pull requests and a weekly Monday schedule.
- **Dependabot:** weekly npm and GitHub Actions update proposals; no automatic merge or npm publication.

Actions use immutable commit pins, read-only repository tokens, hosted runners and checkout without persisted Git credentials. Pull requests use `pull_request`, with no privileged execution of contributor code. See [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).

The initial hosted CI failure was an `ENOTCACHED` registry-metadata miss: `npm ci` caches locked tarballs but does not guarantee the metadata needed for installing an independent consumer. Package verification now uses `--prefer-offline`, which reuses cached content and permits registry access on cache misses. Product snapshot/offline semantics are unchanged. The same installed consumer also executes the full CLI examples.

Linux CI verifies the fixture/package/example suites on a hosted runner; live harness loading, Windows behavior, live Git remote authentication and power-loss durability remain separate certification work.

## Contributions and follow-ups

Use a short-lived branch and pull request against `main`. Required checks cover quality, both candidate runners and dependency audit. Keep issue scope bounded, include reproducible inputs and distinguish generated bytes from actual harness loading. Bug/feature forms and a pull-request template capture those details. Security-sensitive reports should use the private advisory link rather than a public bug issue.

Main protection applies to administrators too, requires up-to-date CI and linear history, and blocks force pushes and deletion. Pull requests are required with zero additional approvals so the sole maintainer can merge their own verified change. Default Actions tokens are read-only and cannot approve pull requests. Dependabot security-fix proposals and private vulnerability reporting are enabled; existing secret scanning and push protection remain enabled.

The existing deferred work is tracked as [live harness certification #1](https://github.com/dills122/veritas/issues/1), [Windows/live Git certification #2](https://github.com/dills122/veritas/issues/2) and [failure/resource hardening #3](https://github.com/dills122/veritas/issues/3). These do not reopen the accepted `0.1.0-rc.0` implementation scope. AI Central links, Serena memories and codebase-memory caches remain local developer tooling and are not CI dependencies.
